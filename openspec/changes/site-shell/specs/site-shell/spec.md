## Purpose

Provides the unified HTML presentation layer that ties all applied features into a navigable three-page static site served via GitHub Pages, giving owners a single URL that works on mobile.

## ADDED Requirements

### Requirement: Three-page site structure
The system SHALL produce three static HTML pages: `site/index.html` (Today), `site/rookies.html` (Rookies & Picks), and `site/reference.html` (Reference). All three pages SHALL be generated by Python scripts during CI builds and committed to the repository. A `site/.nojekyll` file SHALL exist to disable Jekyll processing so `site/static/` is served as-is by GitHub Pages.

#### Scenario: All three pages exist after build
- **WHEN** the GitHub Actions build completes successfully
- **THEN** `site/index.html`, `site/rookies.html`, `site/reference.html`, and `site/.nojekyll` all exist in the repository

#### Scenario: GitHub Pages serves the site directory
- **WHEN** GitHub Pages is configured to serve from the `site/` folder (one-time manual repo setting)
- **THEN** opening the Pages URL loads `site/index.html` (Today) as the default page

### Requirement: Shared design system
The system SHALL include a single shared stylesheet at `site/static/style.css` linked by all three HTML pages. The design system SHALL:
- Use dark surfaces as the primary appearance (not a light design with inverted colors)
- Apply generous spacing between sections to compensate for the lower contrast of dark surfaces
- Use exactly one accent color, applied sparingly and consistently
- Be mobile-first: each page SHALL render as a single readable scrollable column on a 375px-wide viewport before any wider layout rules apply

#### Scenario: Stylesheet is shared
- **WHEN** any of the three pages is opened in a browser
- **THEN** all three pages share the same visual appearance and the stylesheet is loaded from a single shared path

#### Scenario: Mobile layout
- **WHEN** the viewport width is 375px (iPhone SE equivalent)
- **THEN** each page content renders as a single scrollable column with no horizontal overflow

### Requirement: Navigation component
The system SHALL render a navigation component on every page linking to all three pages. On mobile (viewport <= 768px) the navigation SHALL appear as a bottom tab bar in thumb-reach position. On desktop (viewport > 768px) the navigation MAY differ in placement (e.g., top nav) while preserving the same three-link structure. Today (index.html) SHALL be the active page when the site is first opened with no prior navigation state. Each page SHALL highlight its own tab/link as the active item.

#### Scenario: Navigation is present on every page
- **WHEN** any of the three pages is opened
- **THEN** links to all three pages are visible and functional

#### Scenario: Active tab highlighted
- **WHEN** the user opens `site/rookies.html`
- **THEN** the Rookies & Picks navigation item is visually distinguished from the other two items

#### Scenario: Bottom tab bar on mobile
- **WHEN** viewport width is 375px
- **THEN** navigation tabs are positioned at the bottom of the viewport within thumb reach and do not scroll away with page content

### Requirement: Today page content
`site/index.html` SHALL contain two sections rendered from existing cache files: a **News** section sourced from `cache/news.json` and a **Decisions & Votes** section sourced from `data/decisions.json`. Within each section entries SHALL appear in reverse chronological order (most recent first). No entries SHALL be pinned above others based on status (e.g., pending votes do not float to the top).

#### Scenario: News section renders
- **WHEN** `cache/news.json` exists and contains entries
- **THEN** the Today page displays a News section with headlines in reverse chronological order

#### Scenario: Decisions section renders
- **WHEN** `data/decisions.json` exists and contains entries
- **THEN** the Today page displays a Decisions & Votes section with entries in reverse chronological order, each showing its resolution status if resolved

#### Scenario: News section missing cache
- **WHEN** `cache/news.json` does not exist or contains no entries
- **THEN** the News section renders a stale/unavailable notice rather than omitting the section or breaking the page

#### Scenario: Decisions section missing cache
- **WHEN** `data/decisions.json` does not exist or is empty
- **THEN** the Decisions & Votes section renders a placeholder notice rather than omitting the section or breaking the page

### Requirement: Rookies & Picks page content
`site/rookies.html` SHALL contain three sections sourced from existing cache files: **Rising Free Agents** (from `cache/usage.json`), **Pick Tracker** (from `cache/picks.json`), and **Prospect Board** (from `cache/prospects.json` and `cache/consensus.json`). Each section SHALL degrade gracefully when its source cache is missing or stale.

#### Scenario: All three sections render
- **WHEN** all relevant cache files exist and are current
- **THEN** the Rookies & Picks page displays Rising Free Agents, Pick Tracker, and Prospect Board sections in order

#### Scenario: One section cache missing
- **WHEN** `cache/picks.json` is absent but other caches are present
- **THEN** the Pick Tracker section renders a stale/unavailable notice; Rising Free Agents and Prospect Board sections render normally

### Requirement: Reference page content
`site/reference.html` SHALL display league rules content sourced from `cache/league_settings.json` and `data/league_rules_extra.json`. This page replaces `site/rules.md` as the canonical rendered output for the keeper-rules-cheatsheet feature. Each source section SHALL carry a label indicating whether it is auto-synced from Sleeper or manually maintained.

#### Scenario: Reference page renders both sections
- **WHEN** both `cache/league_settings.json` and `data/league_rules_extra.json` exist
- **THEN** the Reference page displays an auto-synced settings section and a manual group agreements section, each with its source label

#### Scenario: League settings cache missing
- **WHEN** `cache/league_settings.json` is absent
- **THEN** the auto-synced section renders a placeholder; the manual section still renders if `data/league_rules_extra.json` exists

### Requirement: Per-section graceful degradation
No single section's missing or stale data SHALL prevent the rest of the page from rendering. Each section SHALL independently check for its data source and render either its content or a bounded notice (e.g., "Data not yet synced" or "Last synced: <timestamp>, may be stale"). A whole-page error or blank page SHALL NOT occur due to a missing cache file.

#### Scenario: Stale data warning
- **WHEN** a cache file's embedded timestamp is more than 24 hours old at render time
- **THEN** that section displays a stale warning alongside its content rather than hiding or replacing it

#### Scenario: Multiple sections missing data
- **WHEN** two or more cache files are absent
- **THEN** each affected section independently shows its own notice; unaffected sections render their content normally

### Requirement: Generator scripts do not modify feature scripts
The three new generator scripts (`generate_today_page.py`, `generate_rookies_page.py`, `generate_reference_page.py`) SHALL only read existing cache and data files — they SHALL NOT modify any existing feature sync script or its output format. All feature scripts remain unchanged.

#### Scenario: Feature script output unchanged
- **WHEN** `generate_today_page.py` is run
- **THEN** `cache/news.json` and `data/decisions.json` are read-only and their format is not altered

### Requirement: No new Python dependencies
The generator scripts SHALL use only packages already present in `requirements.txt` (stdlib, `yaml`, `json`). No new entries SHALL be added to `requirements.txt` for the site-shell capability.

#### Scenario: Requirements unchanged
- **WHEN** site-shell tasks are fully applied
- **THEN** `requirements.txt` contains no new packages compared to before the change

### Requirement: Workflow integration
`sync.yml` SHALL invoke each generator script after its corresponding data sync steps and commit the resulting HTML files alongside cache files. `publish.yml` SHALL invoke `generate_today_page.py` so that decision/vote pushes also regenerate the Today page.

#### Scenario: Today page regenerated on publish
- **WHEN** `publish.yml` runs (triggered by a decision/vote push)
- **THEN** `generate_today_page.py` is executed and `site/index.html` is committed if changed

#### Scenario: All HTML committed after sync
- **WHEN** `sync.yml` runs and data changes
- **THEN** `site/index.html`, `site/rookies.html`, and `site/reference.html` are included in the cache commit alongside their source JSON files
